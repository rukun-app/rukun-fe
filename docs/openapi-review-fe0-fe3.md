# Review kontrak sementara — FE-0 sampai FE-3

Tanggal pemeriksaan: **1 Oktober 2026**. Sumber: [FILE_BE/openapi.json](../FILE_BE/openapi.json), dibandingkan dengan [snapshot generator](../openapi/rukun.json), route, page, query, transport, dan test frontend. Review ini tidak menyatakan backend live telah lulus integrasi atau membuka pengerjaan FE-4.

## Hasil perbandingan

- OpenAPI **3.1.0**, API version **1.0.0**; **126 path, 155 operasi HTTP, 193 schema**.
- Kedua berkas **identik setelah JSON diparse**, termasuk seluruh operasi dan schema. Tidak ada penambahan, penghapusan, atau perubahan kontrak yang memerlukan penggantian snapshot/client.
- Semua `$ref` lokal dapat di-resolve. Ini pemeriksaan referensi, bukan sertifikasi lengkap kepatuhan OpenAPI.
- SHA-256 JSON canonical (keys diurutkan, separator tanpa spasi): `0b883855ab05d5936fdbb2e3a37e365a7f1aaed25d6abf876e0d8410e327463a`.
- Generated client bukan bukti bahwa suatu fitur sudah memiliki UI. Status di bawah didasarkan pada route/page dan pemakaian API di luar direktori generated.

## Kekurangan kontrak dan risiko integrasi yang perlu dipastikan

1. **Transport context belum didokumentasikan.** Tidak ada deklarasi `X-Rukun-Context` dalam JSON ini. Frontend mengirim header untuk context non-global, sedangkan query key ber-context hanya memisahkan cache. Hal itu belum membuktikan response dibatasi ke context terpilih. Beberapa list masih mengandalkan scope backend, bukan filter area aktif. Perlu konfirmasi apakah backend membatasi ke context aktif atau gabungan assignment; tetapkan kontrak dan uji sebelum FE-2/3 ditandai selesai.
2. **Recovery revoked/expired belum lengkap.** HTTP interceptor menangani 401; 403 ditampilkan sebagai error biasa. Belum ada recovery khusus untuk context yang dicabut. Kontrak belum memberi stable error code context invalid/revoked/expired, jadi jangan menyimpulkan setiap 403 berarti seluruh sesi kedaluwarsa.
3. **DTO domain terlalu longgar.** `AreaData`, `HouseholdData`, `ResidentData`, dan `MembershipData` belum mempunyai properti required. Field ID/nama yang UI butuhkan secara teknis optional. Perlu backend menetapkan invariant; frontend harus menyediakan fallback tanpa UUID dan tidak terus loading untuk response kosong/malformed.
4. **Search/sort/total global belum tersedia** di list Community: hanya cursor/per_page dan filter area/household tertentu. AppDataTable mencari/mengurutkan halaman termuat, bukan keseluruhan data. Jangan menambahkan total/count hasil karangan atau filter yang tidak didukung server.
5. **Label relasi belum di-embed.** `HouseholdData` tidak punya nama kepala keluarga; `MembershipData` hanya household ID; area hanya parent ID. UI memakai alamat/nama hasil detail dengan capability, cache/deduplikasi. Untuk skala lebih besar, pertimbangkan DTO ringkasan relasi dari backend agar tidak perlu banyak request detail.
6. **Idempotency tidak seragam.** Population imports/exports menyatakan key required; create area optional; update/delete area dan moveResident tidak mendeklarasikan replay key. Helper frontend mengunci submit dan mengirim key, tetapi exactly-once atau retry setelah timeout harus mengikuti jaminan endpoint, bukan diasumsikan.
7. **Bahasa backend dan UI dapat berbeda.** `/locales` mendokumentasikan `Accept-Language` dan profil menyimpan locale; UI EN sekarang tidak mengubah header ID. Pesan bebas server tidak diterjemahkan oleh frontend. Sinkronisasi harus diuji dan dicatat sebagai pekerjaan FE-1/2 yang tersisa.
8. **Import perlu kontrak operasional tambahan.** Request Community hanya mengandung `area_id`, `file_id` dan format. Urutan upload/poll/download tersedia, tetapi template/kolom dataset, batas ukuran, aturan konflik dan matriks capability harus dikonfirmasi dengan types handler/backend sebelum form siap. Jangan mengambil alih aturan bisnis di frontend.
9. **Menu placeholder masih ada.** Shell warga mempunyai tujuan navigasi di luar fitur yang selesai; `/app/account` dan inbox sendiri belum berfungsi. Sembunyikan/tandai menu belum siap ketika tahap UX berikutnya dikerjakan. Keberadaan route bukan completion gate.

## Urutan tahap berikutnya yang disarankan

Setiap tahap di bawah perlu instruksi pengguna, implementation + unit/browser tests + update README/plan, lalu berhenti untuk testing manual.

1. **Tutup gap FE-1/2:** kontrak context aktif/recovery, sinkronisasi bahasa, penyelesaian reset password; uji isolasi scope nyata. Blocker backend harus dicatat terpisah dari UI yang bisa dikerjakan.
2. **Account warga:** profil, password mandiri, email verification dan sesi perangkat; rapikan beranda warga.
3. **Inbox:** daftar/detail/read state/preferences dengan navigasi context yang valid.
4. **Population transfer:** upload/import/export, progress/result/errors/download; tanpa memasukkan identifier sensitif ke impor biasa.
5. **Administrasi Community:** provisioning/recovery akun, assignment temporal, sensitive reveal/edit dalam tahap yang terpisah sesuai permission.
6. **Gate akhir FE-3:** CRUD dan mutasi backend nyata, multi-assignment/RT/RW/vendor, revocation, audit UX/mobile/a11y/reuse, lalu keputusan lanjut FE-4.

Billing/WiFi/payments tercantum dalam kontrak, tetapi tidak diimplementasikan dalam audit ini. FE-4 dan fase setelahnya tetap belum dimulai.
